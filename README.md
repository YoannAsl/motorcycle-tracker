# ESP32 motorcycle tracker firmware

Rust firmware for an ESP32, a u-blox NEO-7M GPS receiver, and a microSD card. The SD card is the local record. Recording does not depend on Wi-Fi, and confirmed delivery does not immediately remove the local copy.

The firmware uses these terms:

- A **tracking session** begins after the motorcycle has a usable moving GPS fix and ends when the tracker loses power.
- A **track point** is one fresh GPS observation recorded during a tracking session.
- **Pending data** has been recorded locally but has no confirmed remote receipt.
- **Delivered data** has a confirmed remote receipt and may still remain on the SD card.

## Hardware and wiring

Required hardware:

- ESP32 DevKitC with the original ESP32 chip
- u-blox NEO-7M GPS module
- SPI microSD module and a FAT32 card
- automotive-rated, fused 12 V-to-5 V supply for motorcycle installation

Connect all grounds. GPS transmit and receive cross at the ESP32.

| Module | Module signal | ESP32 connection |
| --- | --- | --- |
| NEO-7M | TX | GPIO16, ESP32 RX |
| NEO-7M | RX | GPIO17, ESP32 TX |
| NEO-7M | VCC | 3.3 V |
| NEO-7M | GND | GND |
| microSD | CS | GPIO5 |
| microSD | SCK | GPIO18 |
| microSD | MISO | GPIO19 |
| microSD | MOSI | GPIO23 |
| microSD | VCC | 3.3 V |
| microSD | GND | GND |

The GPS UART runs at 9600 baud. USB serial logging runs at 115200 baud. Format the card as one FAT32 partition with an MBR partition table. Many larger cards ship as exFAT and will not mount.

Confirm that both breakout boards accept 3.3 V power and logic. Keep wiring short, filter the supply, and secure the tracker and antenna away from the motorcycle controls.

## Toolchain

Install Rust first, then install the ESP Rust toolchain and command-line tools:

```sh
rustup toolchain install stable --component rust-src
cargo install espup --locked
espup install
cargo install ldproxy --locked
cargo install espflash --locked
```

On Unix, load the environment generated by `espup` in each new shell:

```sh
. "$HOME/export-esp.sh"
```

On Windows, `espup` installs the environment variables system-wide. Open a new PowerShell session after installation.

ESP-IDF rejects long Windows build paths. If the checkout path is longer than ten characters, use a short target directory in the PowerShell session:

```powershell
$env:CARGO_TARGET_DIR = 'C:\tmp\mt'
```

The checked-in Cargo configuration selects `ldproxy`, enables the ESP-IDF build settings, and pins ESP-IDF v5.5.3 for the `xtensa-esp32-espidf` target.

## Configuration

The firmware reads these values at compile time:

| Variable | Value |
| --- | --- |
| `WIFI_SSID` | Phone hotspot name |
| `WIFI_PASSWORD` | Phone hotspot password |
| `UPLOAD_URL` | `https://` URL ending in `/v1/track-point-batches` |
| `TRACKER_ID` | Stable identity for this tracker |
| `TRACKER_TOKEN` | Bearer token accepted by the upload service |

POSIX shell example:

```sh
export WIFI_SSID='my-phone-hotspot'
export WIFI_PASSWORD='replace-with-hotspot-password'
export UPLOAD_URL='https://uploads.example/v1/track-point-batches'
export TRACKER_ID='motorcycle-tracker-01'
export TRACKER_TOKEN='replace-with-bearer-token'
```

PowerShell example:

```powershell
$env:WIFI_SSID = 'my-phone-hotspot'
$env:WIFI_PASSWORD = 'replace-with-hotspot-password'
$env:UPLOAD_URL = 'https://uploads.example/v1/track-point-batches'
$env:TRACKER_ID = 'motorcycle-tracker-01'
$env:TRACKER_TOKEN = 'replace-with-bearer-token'
```

Set the variables before building because their values are compiled into the firmware. Keep the password, token, tracker identity, and service URL out of commits and logs. `TRACKER_ID` must remain stable so retries identify the same data. TLS certificate validation uses the ESP-IDF certificate bundle enabled in `sdkconfig.defaults`; there is no insecure TLS mode.

## Build, test, flash, and monitor

Run the portable logic tests on the host:

```sh
cargo test
```

Build the ESP32 release firmware:

```sh
cargo +esp build --release --target xtensa-esp32-espidf
```

Connect the ESP32 over USB, then flash it and open the serial monitor:

```sh
cargo +esp run --release --target xtensa-esp32-espidf
```

Cargo invokes the configured runner, `espflash flash --monitor`. To flash the built ELF directly:

```sh
espflash flash --monitor target/xtensa-esp32-espidf/release/motorcycle-tracker
```

If automatic port selection fails, run `espflash list-ports`, set `ESPFLASH_PORT` to the listed device, and retry.

The host tests cover recording, batch selection, HTTPS contracts, retry, restart recovery, diagnostic delivery, and storage cleanup.

## Recording behavior

Booting does not create a tracking session. The firmware checks GPS once per second. A fix qualifies to start a session only when:

- its location is valid and fresh;
- GPS date and time are valid;
- speed is valid and greater than 2 km/h;
- HDOP is valid and no higher than 5.

The third consecutive qualifying fix starts a tracking session and becomes track point 1. The first two fixes are not recorded. Any failed condition resets the count.

After a session starts, every fresh, valid location becomes a raw track point. Stopped points, weak fixes, and missing optional measurements remain in the raw record. Stale or invalid locations do not. CSV and GPX receive a point only when speed is valid and greater than 2 km/h.

Each raw point is appended to NDJSON and flushed before the workflow treats it as recorded. If the body or final newline is short, the firmware closes the file and stops using it. It does not append a newline after a short body. Recovery ignores that incomplete tail and can deliver the earlier complete lines. CSV writes are also flushed. GPX restores the closing XML after every point so it remains parseable after an abrupt power loss.

The ESP32 stores a monotonic tracking-session number in NVS. Point numbers restart at 1 in each session.

## SD card record

A started session gets a directory such as `/session-0000000041/`.

| File | Purpose |
| --- | --- |
| `track-points.ndjson` | Append-only record of every raw track point |
| `gpslog.csv` | Movement-filtered tabular export |
| `gpslog.gpx` | Movement-filtered GPX export kept parseable after every write |
| `session.log` | Boot recovery, session start, minute health records, delivery results, and faults |
| `delivery-state.log` | Append-only confirmed track-point progress |
| `diagnostic-delivery-state.log` | Confirmation that the completed diagnostic log was delivered |

Cleanup writes its own durable record to `/cleanup.log`.

Every NDJSON object contains the schema version, stable tracker ID, session and point numbers, GPS UTC time, latitude, longitude, optional altitude, speed, course, HDOP, satellite count, and ESP32 uptime in milliseconds. Missing optional values are JSON `null`. Non-finite numbers are never serialized.

`session.log` does not duplicate individual track points. Messages also go to the USB serial monitor. Boot messages produced before a session starts are buffered until its log opens.

## HTTPS delivery contract

A background task sends pending data through the phone hotspot without blocking the GPS loop. A shared mutex protects SD access. The task copies at most 30 ordered NDJSON lines into memory and closes the file before DNS, Wi-Fi, TLS, or HTTP work.

Active sessions expose only complete 30-point batches. After a reboot, earlier sessions are inactive, so their final batch may contain fewer than 30 points. The oldest eligible pending data goes first.

Track points use an HTTPS `POST` to `/v1/track-point-batches` with bearer authentication, `Content-Type: application/x-ndjson`, and these headers:

- `X-Track-Point-Schema-Version`
- `X-Tracker-ID`
- `X-Tracking-Session-Number`
- `X-First-Point-Number`
- `X-Last-Point-Number`

The body contains ordered NDJSON objects whose tracker, session, schema, and point numbers match the headers. A response marks the range delivered only when it is 2xx JSON with matching `tracker_id` and `tracking_session_number`, and `highest_stored_point_number` covers the full range. Stable identities and point numbers make retries safe at this boundary.

On a later boot, the firmware sends completed diagnostic logs to the same HTTPS origin at `/v1/diagnostic-logs`. The request has bearer authentication, stable tracker and session headers, and an idempotency key. The log becomes delivered only after a matching 2xx response confirms storage. This repository defines these request and confirmation boundaries, not the remote storage implementation.

## Failure and restart recovery

Wi-Fi, DNS or connection, TLS or certificate, timeout, authentication, other HTTP, transport, malformed response, identity mismatch, incomplete confirmation, and confirmation-persistence failures leave the affected data pending. Diagnostics do not distinguish DNS failure from connection failure.

Point batches and diagnostic logs have separate failure counts. Delays are 15, 30, 60, 120, then 300 seconds for every later failure. If both fail in one pass, the background task uses the shorter delay before checking again. A confirmed and locally persisted success resets that data type's count.

At boot, the firmware scans session directories in number order. Complete NDJSON lines determine the highest recorded point. A partial final line does not count. The last valid checksummed delivery record determines the highest confirmed point. Missing, damaged, mismatched, or impossible progress is ignored, so delivery resumes from the last safe point. An attempted request never counts as delivery.

Recovered sessions are inactive. Their pending points, including final partial batches, and completed pending diagnostic logs become eligible for delivery. Confirmed data stays confirmed. Safe resends rely on the stable HTTPS identities.

## Storage cleanup

Cleanup starts when SD use reaches 80%. It examines inactive sessions oldest first and removes whole directories until use is below 70%.

A directory can be removed only after all its track points and its completed diagnostic log are delivered. The active session and every session with pending data are protected. If protected data prevents cleanup from reaching 70%, the firmware records that condition and continues recording while space remains. It never deletes the only local copy of pending data.

A recoverable cleanup failure is retried after 60 seconds.

## Fault checks

Use the 115200-baud serial monitor with the current session's `session.log`.

- If the SD card does not mount, check FAT32 and MBR formatting, 3.3 V power, common ground, CS GPIO5, and SPI pins 18, 19, and 23.
- If fixes stay stale or no session starts, put the antenna outdoors, check GPS TX to GPIO16 and 9600-baud output, then confirm valid UTC, speed above 2 km/h, and HDOP no higher than 5 for three checks. A cold fix can take several minutes.
- After a raw-point append or flush failure, stop relying on the card until you check its wiring, write protection, filesystem, free space, and health. The failed append does not count as a recorded point.
- For Wi-Fi failures, check the hotspot credentials, range, and whether the phone hotspot is enabled. Local recording should continue and data should stay pending.
- For DNS or connection, authentication, HTTP, TLS, transport, timeout, or malformed confirmation failures, check internet and DNS access, token, URL path, service availability, and the response contract. Do not bypass certificate validation.
- A safe-resend recovery message means delivery progress was absent or damaged. Leave the files intact and allow the stable range to retry.
- If cleanup cannot reach 70%, restore delivery instead of deleting session directories by hand.

## Hardware smoke test

Run this release check with the target ESP32, GPS, microSD module, FAT32 card, phone hotspot, and a test HTTPS service that implements the contract:

- [ ] Cold-boot with the hotspot unavailable. Confirm SD mount and GPS UART messages. Stationary fixes must not create a session.
- [ ] Move with three consecutive qualifying fixes. The third fix must create a session directory and track point 1.
- [ ] Confirm raw NDJSON is flushed and moving points appear in valid CSV and GPX files. Stop or degrade fix quality. Fresh locations must remain raw points while filtered exports skip stopped points.
- [ ] With the hotspot disabled, create two sessions by recording points and cutting power between them. Put more than 30 points in the older session. Enable the hotspot and confirm its first pending 30-point range goes before data from the newer session. Check authentication, metadata, matching confirmation, and persisted progress while recording continues.
- [ ] Induce Wi-Fi, DNS or connection, TLS, timeout, authentication, other HTTP, transport, and malformed or mismatched confirmation failures. Check the retry delays. Recording must continue while the raw file remains writable, and data must stay pending.
- [ ] Cut power with a final batch shorter than 30 points. Restore power while stationary. No false session should start. Recovery must send the older partial batch and completed diagnostic log.
- [ ] Send the same stable batch twice. The service must accept the retry without duplicate points, and local delivery progress must remain correct.
- [ ] Raise test-card use to at least 80%. Cleanup must remove only the oldest fully delivered inactive session directories, stop below 70%, and retain pending data.
- [ ] Check serial output and the delivered diagnostic log for boot recovery, health, delivery, retry, and faults. Check `/cleanup.log` for cleanup results. Point records must not be duplicated in diagnostic logs.

Do not road-test until the tracker, antenna, power converter, fuse, and wiring are secure and cannot interfere with steering, braking, or other controls.
